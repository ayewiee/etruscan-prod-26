# Etruscan — A/B testing platform

The platform is designed for internal (local) deployment in companies that need a platform
where they can manage A/B/.../n experiments in one place, monitor their results, and receive reports.

The automatic `guardrails` system makes it possible to pause or terminate an experiment when certain metrics
reach critical values. The system is flexibly configurable and requires no human intervention after launch.

---

A small Single-Page Application built on `Vue` (`ui/experiment-insights`) was developed for the platform.
The application is a Proof-of-Concept, so it has a simplified interface and lacks the usual authentication — it
is performed by pasting a JWT token into a field on the site.

It is brought up in Docker Compose as one of the services and is available at `localhost:5173`.

## Borrowing and AI usage policy

For the most part, AI was used as an advisor and a souped-up search engine, saving time on googling and searching for answers on StackOverflow.

All code generated by AI (of which there is very little) was thoroughly reviewed and, in most cases, rewritten _)

The API error logic (domain models, mapping, and handling) + the DSL (partially) were taken from **my** project developed during the second qualifying stage.
It is of course not publicly available, but just in case.

## Repository map

- `README.md` – general information about the project.
- `docs/`:
    - `ARCHITECTURE.md` — the current document;
    - `RUNBOOK.md` — launch, health/readiness, and the demo scenario;
    - `TESTING.md` – test commands and structure;
    - `METRICS_AND_GUARDRAILS.md` – details on metrics, the catalog, and guardrails;
    - `TESTING_REPORT.md` — formal testing report (B8);
    - `OPERATIONS.md` — operational readiness and observability (B9);
    - `TRACEABILITY_MATRIX.md` — the "task–criterion–implementation" matrix (B7‑3);
    - `adr/` — the ADR catalog with architectural decisions;
    - `initial/` — the original task + criteria.
- `src/internal/app`:
    - `app.go` – dependency assembly (DI), creating the `App`, starting the GuardrailRunner;
    - `routes.go` – registration of HTTP routes;
    - `server.go` – Echo configuration: error handler, logging, and middleware.
- `src/internal/api`:
    - `handlers/` – HTTP handlers (auth, users, flags, reports ...);
    - `dto/` – request/response DTOs and mappings into domain models;
    - `apierrors/` – error handling and format;
    - `middleware.go`, `context.go`, `pagination.go` – shared API code.
- `src/internal/usecases`:
    - `decide.go` – the main usecase — serving flags, recording decisions;
    - `event.go` – receiving and validating events, deduplication;
    - `report.go` – experiment reports based on the `MetricComputer`;
    - `metric.go`, `metric_compute.go` – the metric catalog and computation of primitive/ratio metrics;
    - `experiment.go`, `experiment_lifecycle.go`, `experiment_review.go`, `experiment_query.go` – experiment lifecycle and review;
    - `guardrail_runner.go` – background running of guardrail checks;
    - `auth.go`, `user.go`, `flag.go`, `event_type.go`, `approver_group.go` – usecases for other entities.
- `src/internal/domain`:
    - `models/` – domain models;
    - `bucketing/` – the `HashAndBucket` function and variant selection `ChooseVariant`;
    - `validation.go` – shared domain validation.
- `src/internal/repository`:
    - `*.go` – wrappers over the generated `sqlc` functions for each entity;
    - `cache/` – Redis repositories (`RunningExperimentCache`, `ParticipationTracker`, `FlagCache`).
- `src/internal/database`:
    - `generated/` – code generated by `sqlc` from SQL files;
    - `src/db/migrations/` – DB schema (migrations) and seed data.
